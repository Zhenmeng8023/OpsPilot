## 1. 结论

原计划书对 V0.7 的方向判断是正确的：下一版本不应该继续堆大型新功能，而应把现有 T1-T8 功能闭环打磨成可测试、可演示、可部署、可维护的稳定版本。

结合当前代码后，V0.7 的实际重点需要调整为：

1. 先补工程化发布骨架：CI、版本接口、版本文件、OpenAPI、Docker/API/Web 发布准备、迁移验证。
2. 再补安全闭环：生产注册开关、权限编码收口、Token 分域测试、Webhook timestamp/nonce、失败事件落库、审计覆盖。
3. 然后做生产可信增强：Email sender、通知重试管理、告警确认/静默/恢复通知、真实主机指标、Webhook 调试页与复杂 matcher。
4. 最后统一前端体验和演示文档：E2E demo、页面状态、错误态、筛选、权限态、Release notes。

当前 `go test ./...` 与 `npm run build` 均已通过，说明 V0.7 可以在当前基础上做收口，不需要大规模重写。

## 3. V0.7 版本目标

V0.7.0 版本定位：稳定化、工程化上线与生产可信能力增强版。

成功标准：

1. 新开发者能按 README/E2E 文档启动 MySQL、Redis、API、Web、Agent，并跑通一次完整演示。
2. CI 能自动执行 Go 测试、Go vet、前端类型检查和构建、Docker 构建、迁移语法检查。
3. `/api/v1/version`、`VERSION`、OpenAPI、CHANGELOG、Release notes 保持一致。
4. 用户 JWT、Agent Token、Webhook Token/Signature 的权限边界有测试覆盖。
5. 告警从触发、确认、静默、恢复到通知有闭环。
6. 通知从站内、HTTP webhook 到 Email 至少三类通道可真实发送并有 delivery 追踪。
7. Webhook 触发失败能被记录、检索和定位。

## 7. 数据库迁移计划

V0.7 新增迁移建议命名：

- `server/migrations/000004_v07_release_security.up.sql`
- `server/migrations/000004_v07_release_security.down.sql`
- 如改动较大，可拆成 `000004` 安全、`000005` 通知告警。

建议字段：

| 表 | 字段/表 | 说明 |
| --- | --- | --- |
| `webhook_sources` | `signing_secret_hash`、`signature_header`、`timestamp_tolerance_seconds` | 触发 token 与签名密钥分离。 |
| `webhook_events` | `nonce`、`failure_reason`、`signature_header` | 支持 timestamp/nonce 调试和失败定位。 |
| `notification_channels` | `config_masked` 或服务端返回 masked view | 不建议长期把 secret 明文回传给前端。 |
| `notification_deliveries` | `provider_message_id`、`last_attempt_at` | 便于邮件/webhook 投递排查。 |
| `alert_rules` | `for_cycles`、`cooldown_seconds`、`notify_on_resolve` | 告警降噪和恢复通知。 |
| `alerts` | `ack_by`、`ack_at`、`silenced_until`、`last_notified_at` | ack/silence/cooldown 闭环。 |
| `alert_silences` | 新表 | 支持 host/rule/severity 范围静默。 |

迁移原则：

1. 不修改历史迁移文件。
2. 新字段必须兼容旧数据，避免无默认值的 NOT NULL。
3. down 迁移必须存在，但允许注明不可逆数据会丢失。
4. 涉及 secret 的字段不回显明文。
