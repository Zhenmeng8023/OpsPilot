## 1. Conclusion

OpsPilot has reached the V0.7 stabilization baseline: Auth/RBAC, Agent/Host, Scripts/Tasks, Realtime Logs, Schedules, Webhooks, Metrics/Alerts/Notifications, Audit, and release engineering all have a verifiable foundation. If the next version is expected to be broad, polished, and product-level, calling it V0.8 understates the scope. The recommended target is V1.0.

V1.0 should upgrade OpsPilot from a set of automation operations capabilities into a governable, observable, workflow-driven operations platform.

Recommended V1.0 themes:

1. **Workflow orchestration center**: connect Script, Task, Approval, Schedule, Webhook, Alert, and Notification into versioned DAG workflows.
2. **Production governance and security**: encrypted secret storage, secret rotation, audit export/retention, and permission/audit coverage checks.
3. **Alert operations and incidents**: move from individual alerts to alert groups, incidents, routing, and suppression.
4. **Long-running metrics lifecycle**: rollups, retention, saved dashboards, and a clean adapter boundary for future time-series stores.
5. **Agent fleet management**: tags/groups, diagnostics, version inventory, maintenance windows, and batch operations.
6. **Product-grade frontend**: unified design system, shared tables/forms/feedback, responsive layouts, and full zh/en language switching.

V1.0 positioning: a formal productization release ready for demo, deployment, long-running operation, and continued extension.

## 3. Product Positioning And Personas

### 3.1 Product Positioning

OpsPilot V1.0 is an automation operations control plane for small teams and production-like environments. It provides:

- Agent onboarding and host governance.
- Script templates, approvals, and task execution.
- Manual, Cron, and Webhook triggers.
- Workflow DAG orchestration.
- Realtime logs and execution audit.
- Host metrics, alerts, incidents, and notifications.
- Security, permission, audit, release, and observability foundations.

## 4. V1.0 Goals

### 4.1 Functional Goals

V1.0.0 succeeds when:

1. Users can create, publish, run, cancel, and retry workflows.
2. Workflows can be triggered manually, by schedules, and by webhooks.
3. Workflows support task, condition, approval, notification, delay, and webhook-call nodes.
4. Workflow run views show node status, timeline, logs, inputs/outputs, errors, and linked task runs.
5. Secrets are encrypted at rest, rotatable, never returned in API responses, and never written to logs/audit.
6. Audit Logs can be exported, retained by policy, and searched with advanced filters.
7. Alerts support grouping, suppression, routing, and incident timelines.
8. Metrics support rollups, retention, and saved dashboards.
9. Agents support tags/groups, diagnostics, version inventory, and maintenance windows.
10. The frontend reaches a consistent, polished, extensible operations-console experience.
11. V1.0 has automated E2E smoke validation and Docker release validation.

### 4.2 Experience Goals

| Area | Goal |
| --- | --- |
| Information architecture | Dashboard shows platform health, recent tasks, critical alerts, Agent state, and workflow state. |
| List pages | Core lists share filters, pagination, empty/error/loading states, refresh, and batch actions. |
| Detail pages | Tasks, workflows, alerts, and webhook events have timelines and linked-resource navigation. |
| Operation feedback | Create, update, delete, pause, resume, retry, and test-send use unified toasts and error displays. |
| Permission states | Hidden menus, disabled actions, 403 pages, and backend rejections stay consistent. |
| i18n | User-visible copy supports zh/en except technical terms such as Agent, Host, Webhook, Metric, SMTP, HMAC, and JSONPath. |
| Responsive behavior | Desktop first, usable on tablet/narrow screens, no overlapping controls or overflowing text. |

## 6. Architecture Design

### 6.1 Target Architecture

V1.0 keeps the monolithic Go API and modular React frontend. The priority is strong module boundaries and testable business cores, not microservices.

```text
React Web
  ├─ Shared UI / i18n / auth guard
  ├─ Dashboard
  ├─ Agents / Scripts / Tasks / Logs
  ├─ Workflows
  ├─ Schedules / Webhooks
  ├─ Metrics / Alerts / Incidents
  ├─ Notifications
  └─ Audit / Settings

Go API
  ├─ app/router + middleware
  ├─ auth / rbac / audit / security
  ├─ agents / scripts / tasks / execution / logs
  ├─ workflows / workflow executor
  ├─ schedules / webhooks
  ├─ metrics / alerts / incidents
  ├─ notifications / templates / dispatcher
  └─ platform db / redis / config / crypto

Agent
  ├─ register / heartbeat / metrics
  ├─ task claim / execution / logs / result
  └─ diagnostics / version / maintenance state
```

### 6.2 Workflow Execution Model

Workflow execution must be versioned and immutable.

Objects:

- `workflow_definition`: business identity, name, status, current version.
- `workflow_version`: immutable DAG JSON, version number, checksum, publisher.
- `workflow_run`: one execution, trigger source, input, status, output, error.
- `workflow_node_run`: one node execution, status, attempts, linked task run, input/output, error.
- `workflow_trigger_binding`: Manual/Schedule/Webhook binding to workflow version.

Rules:

1. A run always reads a fixed `workflow_version`.
2. DAG validation rejects cycles, missing entries, invalid node types, and missing parameters.
3. Node states: `pending -> ready -> running -> success|failed|skipped|canceled|timeout`.
4. Workflow state is aggregated from node state.
5. Failure policy supports `stop_workflow`, `continue`, and `skip_downstream`.
6. Retry supports max attempts, interval, and exponential backoff.
7. Workflow cancellation propagates to linked task runs.
8. Retry resumes from failed nodes by default.

### 6.3 Security Governance

V1.0 must remove plaintext secrets from long-term storage and display paths.

Principles:

- Store secrets with application-level envelope encryption.
- Never return plaintext secrets from API.
- Never write plaintext secrets to audit or logs.
- Track rotation version and time.
- Reject secret writes in production when encryption key config is missing.
- Keep key id in the data model for future KMS integration.

### 6.4 Alert/Incident Model

V1.0 should add an incident/group layer on top of alerts:

- Alert: state machine for a single fingerprint.
- Alert group: aggregation by rule, host group, severity, or fingerprint.
- Incident: human-facing event view containing one or more alert groups.
- Suppression: suppresses notifications without deleting alerts.
- Routing policy: maps severity/rule/host group to channel/template.

### 6.5 Metrics Lifecycle

Short-term MySQL storage remains acceptable, but growth must be controlled:

- Keep raw metrics for a short period.
- Keep 5m/1h rollups for longer periods.
- Trend queries choose raw or rollup data by time range.
- Cleanup jobs support dry-run.
- Cleanup/archive operations write audit logs.

## 7. Frontend UI/UX Design

### 7.1 Navigation

| Governance | Audit Logs, Users, Roles, Settings |

### 7.2 Dashboard

The first screen must be the usable console, not a landing page. Recommended widgets:

- Platform health: API, DB, Redis, Agent online rate.
- Active incidents by severity.
- Recent workflow runs.
- Recent task runs and failure rate.
- Agent fleet summary.
- Notification delivery status.
- Recent high-risk audit events.

### 7.3 Visual Theme

- Neutral base colors plus semantic green/red/yellow/blue.
- Dense but readable operations-console layout.
- Cards only for repeated items, summary metrics, modals, and tool panels.
- Border radius 8px or less.
- Restrained headings inside dashboards and tools.
- Charts must support diagnosis, not decoration.
- Use lucide icons for icon buttons with tooltips.

### 7.4 Shared Components

V1.0 should provide:

- `DataTable`
- `FilterToolbar`
- `ConfirmDialog`
- `ToastCenter`
- `StatusBadge`
- `Timeline`
- `JsonViewer`
- `SecretField`
- `PermissionGate`
- `PageHeader`

### 7.5 Workflow UI

Reliability comes before visual complexity.

Recommended path:

1. Start with a structured DAG editor: node list, dependency view, parameter panel.
2. Add canvas editing later: drag nodes, connect edges, zoom, auto layout.

Required behavior:

- Add, delete, copy, and disable nodes.
- Edit and validate node parameters.
- Configure dependencies.
- Locate DAG validation errors.
- Preview before publish.
- Show run timeline after execution.
- Retry failed nodes.
- Link nodes to task runs/logs.
- Support zh/en copy.

### 7.6 Responsive And Accessibility

- Every form control has a label or aria-label.
- Tables scroll horizontally on narrow screens.
- Long IDs, payloads, and errors wrap or use monospace panels.
- Dangerous actions are keyboard-focusable and confirmed.
- Toasts do not block key actions.
- Empty states explain the current result, not the whole feature.
