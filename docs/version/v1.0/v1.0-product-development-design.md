## 1. 结论

OpsPilot 当前已经完成 V0.7 稳定化主线：Auth/RBAC、Agent/Host、Scripts/Tasks、Realtime Logs、Schedules、Webhooks、Metrics/Alerts/Notifications、Audit 和 Release 工程化都具备可验证基础。下一版本如果继续称为 V0.8，会低估实际改动范围；如果目标是“功能全面、UI 美化完善、修改幅度大且跟进内容多”，建议直接规划为 V1.0。

V1.0 的核心目标不是再补几个孤立接口，而是把 OpsPilot 从“自动化运维功能集合”升级为“可编排、可治理、可观测、可持续运行的自动化运维平台”。

V1.0 建议聚焦六条主线：

1. **Workflow 编排中枢**：用可视化或结构化 DAG 把 Script、Task、Approval、Schedule、Webhook、Alert、Notification 串成完整流程。
2. **生产治理与安全**：补 secret 加密存储、rotation、Audit export/retention、权限与审计覆盖复核。
3. **告警运营和事件化**：把单条 alert 升级为 alert group / incident / routing / suppression 的运营模型。
4. **指标长期运行能力**：补 metrics rollup、retention、saved dashboard，为后续外部时序库适配预留边界。
5. **Agent fleet 管理**：补 tags/groups、diagnostics、version inventory、maintenance window 和批量管理。
6. **前端产品化 UI**：建立统一设计系统、共享表格/表单/反馈组件、移动/桌面响应式、完整 zh/en language switching。

V1.0 的版本定位：正式产品化版本，面向可演示、可部署、可长期运行、可扩展二次开发。

## 4. V1.0 版本目标

### 4.1 总体目标

V1.0.0 的成功标准：

1. 用户可以创建、发布、执行、取消、重试 Workflow。
2. Workflow 可以由 Manual、Schedule、Webhook 触发。
3. Workflow 支持 task、condition、approval、notification、delay、webhook call 等基础节点。
4. Workflow run 可视化展示节点状态、时间线、日志、输入输出、错误和关联 task_run。
5. Secret 加密存储、可轮换、不可回显，审计和日志不泄露明文。
6. Audit Logs 可导出、可设置 retention、可按更复杂条件检索。
7. Alerts 支持 grouping、suppression、routing，并形成 incident timeline。
8. Metrics 支持 rollup、retention 和 saved dashboard。
9. Agent 支持 tags/groups、diagnostics、version inventory 和 maintenance window。
10. 前端 UI 达到统一、专业、可扩展的运维控制台体验。
11. V1.0 具备自动化 E2E smoke 和 Docker 发布验收。

## 6. 总体架构设计

### 6.1 目标架构

V1.0 继续保持单体后端和模块化前端，不做微服务拆分。架构重点是清晰模块边界和可测试业务核心。

```text
React Web
  ├─ Shared UI / i18n / auth guard
  ├─ Dashboard
  ├─ Agents / Scripts / Tasks / Logs
  ├─ Workflows
  ├─ Schedules / Webhooks
  ├─ Metrics / Alerts / Incidents
  ├─ Notifications
  └─ Audit / Settings

Go API
  ├─ app/router + middleware
  ├─ auth / rbac / audit / security
  ├─ agents / scripts / tasks / execution / logs
  ├─ workflows / workflow executor
  ├─ schedules / webhooks
  ├─ metrics / alerts / incidents
  ├─ notifications / templates / dispatcher
  └─ platform db / redis / config / crypto

Agent
  ├─ register / heartbeat / metrics
  ├─ task claim / execution / logs / result
  └─ diagnostics / version / maintenance state
```

### 6.2 Workflow 执行模型

Workflow 应使用不可变版本执行，避免用户修改定义后影响历史 run。

核心对象：

- `workflow_definition`：业务身份、名称、状态、当前发布版本。
- `workflow_version`：不可变 DAG JSON、版本号、checksum、发布人。
- `workflow_run`：一次执行实例，记录触发来源、输入、状态、输出、错误。
- `workflow_node_run`：节点执行实例，记录节点状态、尝试次数、关联 task_run、输入输出和错误。
- `workflow_trigger_binding`：Manual/Schedule/Webhook 到 workflow version 的绑定。

执行规则：

1. 运行时读取固定 `workflow_version`。
2. 校验 DAG 无环、有入口、有出口、节点引用合法。
3. 节点状态：`pending -> ready -> running -> success|failed|skipped|canceled|timeout`。
4. Workflow 状态由节点状态聚合：`pending/running/success/failed/canceled/timeout`。
5. 节点失败策略支持 `stop_workflow`、`continue`、`skip_downstream`。
6. 节点重试支持最大次数、间隔、指数退避。
7. Workflow cancel 必须向关联 task_run 传播取消。
8. Workflow retry 默认从失败节点继续，不重复已成功节点，除非用户选择重新运行。

### 6.3 安全治理模型

V1.0 必须把 secret 明文从长期存储和展示链路中移除。

原则：

- 数据库存储 secret 时使用应用层 envelope encryption。
- API 永不返回明文 secret。
- Audit/log 永不保存明文 secret。
- rotation 有版本和时间记录。
- 加密 key 缺失时，生产环境拒绝写入 secret。
- 加密 key 管理不引入复杂 KMS 依赖，但接口预留 key id。

### 6.4 Alert/Incident 模型

V1.0 应在 `alerts` 之上新增 incident/group 视角。

- Alert：单个 fingerprint 的状态机。
- Alert group：按 rule/host group/severity/fingerprint 聚合。
- Incident：面向人处理的事件视图，可包含一个或多个 alert group。
- Suppression：根据规则抑制通知，不删除 alert。
- Routing policy：根据 severity/rule/host group 选择 channel/template。

### 6.5 Metrics 生命周期

短期仍使用 MySQL，但必须控制增长：

- 明细 metrics 保留短周期。
- 5m/1h rollup 保留长周期。
- 趋势查询根据时间范围选择明细或 rollup。
- 清理任务必须支持 dry-run。
- 删除或归档必须写审计。

## 7. 前端 UI/UX 设计要求

### 7.1 信息架构

V1.0 建议导航分组：

| 分组 | 页面 |
| --- | --- |
| Overview | Dashboard、Activity、Global Search |
| Automation | Workflows、Workflow Runs、Scripts、Tasks、Schedules、Webhooks |
| Fleet | Agents、Hosts、Enrollment Tokens、Diagnostics |
| Observability | Metrics、Alerts、Incidents、Notifications |
| Governance | Audit Logs、Users、Roles、Settings |

### 7.2 Dashboard 首屏

首屏应是实际控制台，不做营销页。建议模块：

- Platform health：API、DB、Redis、Agent online rate。
- Active incidents：按 severity 分组。
- Workflow runs：最近成功/失败/运行中。
- Task runs：最近任务和失败率。
- Agent fleet：在线、离线、维护中。
- Notification delivery：failed/pending/success。
- Audit risk events：近期高风险操作。

### 7.3 视觉主题

UI 应保持专业运维控制台风格：

- 颜色：中性底色 + 绿色/红色/黄色/蓝色语义色，不使用单一紫色或大面积渐变。
- 密度：信息密度适中，强调扫描效率。
- 卡片：只用于重复项、概览指标、弹窗和工具面板，避免卡片套卡片。
- 圆角：保持 8px 或以下，符合工具型产品。
- 字体：不使用 viewport-width 动态字号；控制台内标题克制。
- 图表：趋势、状态、事件分布要服务诊断，不做装饰图。
- 图标：按钮优先使用 lucide icons，图标按钮有 tooltip。

### 7.4 共享组件

V1.0 必须沉淀：

- `DataTable`：列定义、排序、分页、empty/error/loading。
- `FilterToolbar`：keyword、select、date range、reset、refresh。
- `ConfirmDialog`：危险操作、批量操作、二次确认。
- `ToastCenter`：成功、失败、后台任务提示。
- `StatusBadge`：统一状态颜色和文案。
- `Timeline`：task/workflow/incident/audit 通用时间线。
- `JsonViewer`：payload、before/after、metadata 展示。
- `SecretField`：masked、rotate、copy-once。
- `PermissionGate`：按钮/区域权限控制。
- `PageHeader`：标题、说明、主操作、面包屑。

### 7.5 Workflow UI

Workflow 编辑器优先目标是可靠，而不是炫技。

可选实现路线：

1. 第一阶段使用结构化 DAG 编辑器：左侧节点列表，中间依赖关系，右侧参数面板。
2. 第二阶段再加入画布：拖拽节点、连线、缩放、自动布局。

必须支持：

- 节点添加、删除、复制、禁用。
- 节点参数编辑和校验。
- 连线/依赖配置。
- DAG validation 错误定位。
- 发布前 preview。
- 运行后 timeline。
- 失败节点重试。
- 节点关联 task_run/log 跳转。
- zh/en 文案。

### 7.6 响应式与可访问性

- 所有表单控件必须有 label 或 aria-label。
- 表格在窄屏使用横向滚动，不挤压文字。
- 长 ID、payload、错误信息必须可折行或使用 monospace 区域。
- 危险操作必须可键盘聚焦并有确认。
- Toast 不遮挡关键操作。
- 空态必须说明当前筛选下无结果，不写功能说明长文案。

| 发布 | Docker build/compose、CI、迁移、OpenAPI diff、E2E smoke 都通过了吗？ |
| UI | Dashboard、Workflow、Tasks、Alerts、Notifications、Audit 的主题、表格、筛选、反馈、响应式是否统一？ |
| i18n | 除专业术语外，用户可见文案是否支持 zh/en？ |
| Secret | SMTP password、webhook secret、channel token 是否加密存储且不可回显？ |
| Audit | 审计能导出吗？retention 有 dry-run 和审计记录吗？ |
| Workflow | 能创建、发布、手动触发、Schedule 触发、Webhook 触发 Workflow 吗？ |
| Workflow Run | run/node run 状态、日志、失败原因、取消、重试都可见吗？ |
| 权限 | `workflow:read/manage/execute` 和现有权限是否前后端一致？ |
| Webhook | JSONPath matcher 和 simulator 能定位复杂 payload 匹配问题吗？ |
| Notifications | Template 能渲染、测试发送、绑定渠道并用于 delivery 吗？ |
| Alerts | Grouping、suppression、routing、incident 是否减少重复通知？ |
| Metrics | Rollup/retention 是否限制明细表长期增长？ |
| Agent | Tags/groups、diagnostics、version inventory、maintenance window 是否可用？ |
| Release | README、CHANGELOG、Release notes、OpenAPI、VERSION 是否一致？ |
