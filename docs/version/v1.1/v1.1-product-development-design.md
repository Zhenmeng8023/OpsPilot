# OpsPilot V1.1 下一版本设计

生成日期：2026-05-09

## 1. 版本定位

V1.1 不再以补齐大功能为主，而是把 V1.0 已经闭环的自动化运维平台推向更适合真实生产值班的形态。核心关键词是：可靠运行、快速排障、规模化 Agent 管理、告警治理、可验证 UI 回归。

V1.1 的目标不是重构架构，也不是引入多租户、AI 诊断或外部时序数据库。它应该沿用 V1.0 的单体 Go API、React 控制台、MySQL/Redis 和 Agent 模型，在现有模块边界内提高生产使用质量。

## 2. 设计原则

1. 先增强可诊断性，再增加复杂能力。生产运维系统最大的成本通常不是创建任务，而是失败后定位链路。
2. 优先建设跨模块视图。V1.0 已有 Workflow、Task、Webhook、Audit、Notification、Alert，但缺少一个贯穿它们的 trace 视角。
3. 后端状态机必须比前端交互更可信。所有重试、取消、恢复、审批和抑制行为都要能从服务端审计。
4. UI 回归证据要自动化。V1.1 起关键页面不能只依赖 `npm run build`，需要 Playwright smoke 和截图留档。
5. 不做破坏性迁移。V1.1 所有数据结构应兼容 V1.0，新增字段必须有默认值或允许为空。

## 3. P0 主线

### 3.1 全局 Trace Center

目标：用户输入 `traceId`、workflow run id、task run id、webhook event id、alert id 或 notification id 后，可以看到一次操作从触发到执行、通知、审计的完整链路。

范围：

- 新增 `GET /api/v1/traces/:id` 聚合接口。
- 聚合 workflow run、workflow node run、task run、task target、webhook event、schedule trigger、notification delivery、audit log、alert/incident timeline。
- 前端新增 Trace Center 页面，支持一键从各详情页跳转。
- 所有关键页面展示 traceId 并提供复制。

验收：

- manual workflow、schedule workflow、webhook workflow 三条路径都能生成完整 trace。
- 失败节点、取消 run、notification retry 都能在 trace timeline 中显示。
- audit 中能反查同一 trace 下的用户动作。

### 3.2 Workflow 运行可靠性增强

目标：让 Workflow 不只是能跑通，还能在失败后被安全恢复、解释和复盘。

范围：

- Workflow run diff：展示当前 definition version 与执行 version 的差异摘要。
- Retry plan preview：重试前展示将重跑哪些节点、哪些成功节点会跳过。
- Cancel propagation report：取消后展示哪些 task target 已取消、哪些仍在收敛。
- Node output summary：保存节点输出摘要，避免用户必须打开完整日志。
- Workflow run search：按状态、触发源、时间、发起人、关键字筛选。

验收：

- 失败后从失败节点重试不会重复已成功节点。
- 取消运行中 task 节点后，task target 状态和 workflow node 状态最终一致。
- 前端可以解释每次 retry/cancel 的影响范围。

### 3.3 Playwright UI Smoke 与截图证据

目标：把 V1.0 的“构建通过”升级为“关键页面可打开、可截图、可回归”。

范围：

- 引入 Playwright 配置和 smoke 脚本。
- 覆盖 Dashboard、Workflow、Agents、Metrics、Notifications、Audit、Webhooks。
- 使用 seed 数据或 API setup 创建最小可视化状态。
- CI 上传截图 artifact。
- 截图路径写入 release evidence。

验收：

- desktop 与 narrow viewport 都能打开关键页面。
- 无明显文本溢出、空白页面、JS runtime error。
- CI 失败时保留 screenshot 和 trace artifact。

## 4. P1 主线

### 4.1 Agent Fleet 规模化治理

范围：

- Agent version distribution 视图。
- Agent stale reason：区分心跳超时、token 失效、禁用、网络不可达、版本过旧。
- Host Group 动态规则草案：按 tag、hostname 前缀、OS 类型匹配候选主机。
- 批量维护窗口 preview：创建前展示受影响 Agent/Host。
- Agent diagnostics diff：比较最近两次诊断快照。

验收：

- 运维人员能快速判断哪些 Agent 需要升级或排查。
- 批量操作前能看到影响范围。

### 4.2 告警与 Incident 治理

范围：

- Incident 手动创建、合并、关闭。
- Alert group 到 incident 的关联与解除。
- Routing hit explanation：解释某条告警命中了哪个 routing/suppression rule。
- Noise report：按规则、主机组、严重级别统计近 24h/7d 告警噪声。
- Maintenance impact report：维护窗口期间抑制了哪些告警、跳过了哪些调度。

验收：

- 值班人员能从 incident 页面看到告警来源、处理记录、通知投递、关联任务。
- 抑制和路由行为可解释、可审计。

### 4.3 安全与合规加固

范围：

- Secret rotation history，记录轮换时间、操作者、key id，不回显明文。
- 敏感配置变更二次确认。
- 权限变更影响预览：显示将新增/移除哪些能力。
- Audit export 增加 hash 摘要，便于归档校验。
- 高危 workflow/template 操作写入更明确的 audit action。

验收：

- 任意 secret 变更都有审计记录。
- 权限变更前能看到差异。
- 导出的审计文件可校验完整性。

## 5. P2 探索项

这些能力可以设计接口边界，但不应阻塞 V1.1：

- Workflow template marketplace 的最小雏形。
- 外部时序数据库 adapter 设计草案。
- OIDC/SSO 登录预研。
- Agent 自动升级协议草案。
- ChatOps 告警确认入口。

## 6. 数据模型建议

建议新增或扩展：

- `trace_events`：可选的轻量索引表，用于跨模块 timeline 聚合缓存。
- `workflow_run_actions`：记录 retry/cancel/approve/reject 等运行期动作。
- `ui_smoke_runs`：记录本地或 CI 的页面截图验收结果，可先只存 artifact metadata。
- `incident_alert_groups`：incident 与 alert group 多对多关系。
- `secret_rotation_events`：secret 轮换历史，不保存明文。

约束：

- 所有新增表必须有 up/down 迁移。
- 新字段不能破坏 V1.0 数据。
- 对历史大表的索引新增要评估查询条件，避免无意义索引。

## 7. API 设计方向

建议新增接口：

- `GET /api/v1/traces/:id`
- `GET /api/v1/workflows/runs/:id/retry-plan`
- `GET /api/v1/workflows/runs/:id/action-history`
- `GET /api/v1/agents/version-distribution`
- `GET /api/v1/agents/:id/diagnostics/diff`
- `GET /api/v1/alerts/routing-explain/:alertId`
- `GET /api/v1/incidents/:id/timeline`
- `POST /api/v1/incidents/:id/alert-groups`
- `GET /api/v1/security/permissions/diff`

API 必须继续通过 OpenAPI/router diff 检查。

## 8. 前端信息架构

新增或强化页面：

- Trace Center：全局排障入口。
- Workflow Run Detail：加入 retry plan、action history、definition diff。
- Agent Fleet Overview：版本分布、异常原因、诊断差异。
- Incident Detail：值班处理视图、告警组、通知、审计 timeline。
- Security Review：权限差异和 secret rotation history。
- UI Smoke Evidence：展示最新截图验收结果，可先作为文档 artifact 链接。

UI 继续保持 V1.0 的控制台风格，不做营销页，不做大面积装饰布局。

## 9. 交付节奏

建议 5 周：

1. 第 1 周：Trace Center 后端聚合、traceId 页面入口、OpenAPI。
2. 第 2 周：Workflow retry/cancel/action history 加固。
3. 第 3 周：Playwright UI smoke、截图 artifact、CI 接入。
4. 第 4 周：Agent Fleet 与 Incident 治理。
5. 第 5 周：安全合规加固、文档、发布验收。
